1. Stack Tecnológica e Linguagens

1Que linguagens de programação foram usadas neste projecto?

O projecto usa quatro linguagens principais:

  • TypeScript — linguagem principal do frontend (React Native, Electron) e das Edge Functions (Deno). TypeScript é JavaScript com tipagem estática.
  • SQL / PL/pgSQL — linguagem do backend: definição das tabelas, políticas de segurança (RLS), funções armazenadas, triggers e agendamentos (pg_cron).
  • JavaScript — configurações de build (Metro, Vite), scripts auxiliares.
  • HTML5 + CSS3 — estrutura e estilo da versão PWA/Web.
Resumo: TypeScript no frontend/lógica de negócio + SQL/PL/pgSQL no backend (base de dados). Não há servidor Node.js ou PHP separado — o Supabase actua como BaaS (Backend-as-a-Service).
2O que é TypeScript e por que usou TypeScript em vez de JavaScript?

TypeScript é JavaScript com tipagem estática — desenvolvido pela Microsoft. Em vez de descobrir erros apenas quando o app corre (runtime), o TypeScript detects-os em tempo de desenvolvimento (compile time). Benefícios neste projecto:

  • Segurança de tipos: ao aceder à base de dados, os tipos das colunas SQL são mapeados automaticamente para tipos TypeScript via supabase-js.
  • Autocomplete: o editor sugere campos disponíveis, reduzindo erros de digitação.
  • Refactoring seguro: ao mudar um nome de campo, o compilador aponta todos os locais afectados.
  • Padrão da indústria: React Native, Expo e Supabase são todos escritos em TypeScript.
3O que é React Native e por que foi escolhido para o frontend?

React Native (Meta/Facebook) é uma framework que permite escrever uma única base de código em TypeScript/JavaScript e compilar para Android, iOS e Web. Benefícios:

  • Um único developer consegue criar app para 3 plataformas.
  • Componentes nativos reais (não WebView) — performance próxima de uma app nativa.
  • Grande ecossistema: 100 000+ bibliotecas no npm.
  • Expo simplifica o build sem necessidade de Mac para compilar iOS.
Trade-off honesto: React Native tem limitações em funcionalidades de hardware avançadas (Bluetooth, NFC) comparado com desenvolvimento nativo puro em Java/Kotlin ou Swift.
4O que é o Expo e qual a diferença para React Native puro?

Expo é uma plataforma built on top de React Native que adiciona:

  • EAS Build: serviço cloud que compila o APK Android sem precisar de instalar Android Studio localmente.
  • Expo Go: app de teste rápido no telemóvel, sem instalar o APK completo.
  • APIs unificadas: câmera, notificações, ficheiros — mesma API em Android e iOS.
  • OTA Updates: actualizar o JavaScript da app sem publicar nova versão na loja.

Neste projecto, foi usado Expo SDK 54 com Expo Router para navegação baseada em ficheiros (semelhante a Next.js).

5O que é PL/pgSQL e onde foi usado?

PL/pgSQL (Procedural Language/PostgreSQL) é a linguagem de programação procedural nativa do PostgreSQL. Permite escrever funções, stored procedures e triggers directamente na base de dados. Foi usado para:

  • handle_new_user() — trigger que cria automaticamente o perfil quando um utilizador se regista via Supabase Auth.
  • fn_audit_trigger() — trigger que regista todas as alterações de dados no audit log.
  • is_admin(), is_secretario(), is_healthcare_pro() — funções de verificação de papel usadas nas políticas RLS.
  • admin_report_stats() — função que agrega estatísticas para o dashboard do admin.
Vantagem: a lógica de negócio crítica (verificação de permissões, auditoria) vive na base de dados e não pode ser contornada por um cliente malicioso.
6O que são Edge Functions e que linguagem usam?

Edge Functions são funções serverless que correm no servidor do Supabase, em resposta a eventos HTTP. Usam Deno como runtime (alternativa ao Node.js, desenvolvida pelo mesmo criador, com suporte nativo a TypeScript). Foram usadas para:

  • send-email: chama a API Resend para enviar emails de lembrete de consulta.
  • send-whatsapp: chama a WhatsApp Business Cloud API para lembretes via WhatsApp.

São invocadas por pg_cron (agendador SQL) ou directamente pelo cliente via HTTP POST.

7O que é o Supabase e é realmente um "backend"?

Supabase é um Backend-as-a-Service (BaaS) open-source, alternativa ao Firebase mas baseado em PostgreSQL. Inclui:

ComponenteEquivalente tradicional
PostgreSQLServidor de base de dados (MySQL, Oracle)
PostgRESTAPI REST gerada automaticamente das tabelas
Supabase AuthServidor de autenticação (JWT, OAuth)
RealtimeWebSocket server (Socket.io)
StorageFile server (AWS S3)
Edge FunctionsServidor Node.js/PHP (AWS Lambda)
Sim, é um backend completo — simplesmente não foi necessário escrever um servidor Express/Node.js separado porque o Supabase providencia essas camadas já configuradas.
8Como funciona o Electron para a versão Desktop?

Electron (GitHub/Microsoft) empacota uma aplicação web (HTML/CSS/JavaScript) junto com o motor Chromium e um runtime Node.js, criando um executável nativo (.exe no Windows). Assim, o mesmo código React Native Web é usado para criar a app Desktop. Permite:

  • Acesso ao sistema de ficheiros local.
  • Notificações de sistema nativas do Windows.
  • Instalador NSIS (.exe) para distribuição sem loja de aplicações.
Desvantagem: o tamanho do instalador é maior (~80–150 MB) porque inclui o Chromium. Apps nativas em C++ seriam menores, mas exigiriam desenvolvimento separado.
9O que é uma PWA (Progressive Web App)?

Uma PWA é um website com capacidades de app nativa. Características implementadas:

  • Service Worker: cache inteligente que permite uso parcial offline.
  • Web App Manifest: o browser oferece "Instalar" no ecrã inicial.
  • Web Push Notifications: notificações mesmo com o browser fechado.
  • HTTPS obrigatório — deploy no Vercel garante SSL automático.
10Por que não usou Flutter/Dart ou Java/Kotlin nativo?

Decisão baseada em 3 factores:

  • Partilha de código: com React Native + Expo Router, um único código funciona em Android, iOS, Windows (Electron) e Web. Flutter também suportaria, mas o ecossistema de bibliotecas TypeScript para Supabase é mais maduro.
  • Integração Supabase: a biblioteca oficial @supabase/supabase-js é TypeScript-first — tipagem automática das queries SQL.
  • Curva de aprendizagem: TypeScript/React é o ecossistema mais utilizado globalmente (Stack Overflow Survey 2024).
Java/Kotlin nativo seria mais performático, mas exigiria equipa separada para Android, iOS e Desktop — inviável para um projecto individual.

2. Arquitectura e Backend

11Explique a arquitectura geral do sistema.

Arquitectura de 3 camadas:

  • Camada de Apresentação: React Native (Mobile/Desktop/Web) + Electron. Comunica com o backend via SDK TypeScript do Supabase sobre HTTPS/WSS.
  • Camada de Negócio/API: Supabase — PostgREST gera endpoints REST automáticos; Row Level Security aplica regras de acesso ao nível da base de dados; Edge Functions para lógica custom.
  • Camada de Dados: PostgreSQL 15 — armazena todos os dados clínicos, utilizadores, agendamentos, audit logs. pg_cron para tarefas agendadas.
Padrão: Client → Supabase SDK → PostgREST → PostgreSQL (com RLS). A lógica de autorização está na camada de dados, não no cliente.
12O que é o PostgREST e como gera a API automaticamente?

PostgREST é um servidor web que inspecciona o schema do PostgreSQL e gera uma API RESTful automaticamente. Por exemplo:

  • Tabela public.profiles → GET /rest/v1/profiles retorna os registos.
  • Row Level Security do PostgreSQL aplica-se a cada request — o utilizador autenticado só vê os seus dados.
  • Não é necessário escrever código de controller/router como num backend Express.
13Como é feita a autenticação no sistema?

O sistema usa JWT (JSON Web Token) via Supabase Auth:

  • Utilizador envia email/password → Supabase valida → retorna um JWT assinado.
  • O JWT contém o user_id (UUID), email, papel (role) e data de expiração.
  • Cada request à API inclui o token no header Authorization: Bearer <token>.
  • O PostgreSQL expõe auth.uid() — a função que retorna o UUID do utilizador actual.
  • As políticas RLS usam auth.uid() para filtrar dados: WHERE paciente_id = auth.uid().
14Como funciona o Realtime do Supabase?

Supabase Realtime usa WebSocket (protocolo WSS) + extensão PostgreSQL pg_logical. Funciona assim:

  • O cliente subscreve a uma tabela ou query específica: supabase.channel('appointments').on('postgres_changes', ...)
  • Quando há INSERT/UPDATE/DELETE na tabela, o PostgreSQL notifica via replication log.
  • O servidor Realtime envia o evento pelo WebSocket para todos os clientes subscritos.

Resultado: alteração da secretária no Windows aparece em <1 segundo no app Android do dentista.

14BComo funciona o sistema de Presença em Tempo Real (Online/Offline) no Chat?

O sistema de presença garante a monitorização precisa do estado activo de dentistas, secretários e pacientes em Web, PWA e Mobile:

  • Supabase Realtime Presence: utiliza o canal WebSocket presence-global. Ao entrar na app, o cliente executa presenceChannel.track({ user_id, online_at }).
  • Multi-plataforma & Ciclo de Vida:
    • Mobile (Android/iOS): escuta o AppState do React Native. Quando a app entra em segundo plano (background) ou ecrã bloqueado, executa untrack() (Offline). Ao voltar ao primeiro plano (active), re-efectua track() (Online).
    • Web & PWA: monitoriza os eventos document.visibilityState e window.onblur/onfocus para detectar se o separador está activo.
  • Sincronização na UI: o PresenceContext consome os eventos sync, join e leave, renderizando badges em tempo real (ponto verde ● Online ou cinzento ○ Offline) no cabeçalho do chat e na lista de conversas.
Resultado: a presença é 100% precisa e sincronizada instantaneamente entre o navegador web da secretária e a app mobile do dentista.
15Como funciona o sistema de lembretes automáticos?

Sistema de 3 camadas redundantes para garantir que lembretes são sempre enviados:

  • Camada 1 — pg_cron (servidor): job SQL que corre de hora em hora, verifica consultas nas próximas 24h e chama a Edge Function via pg_net.http_post().
  • Camada 2 — Edge Function: função TypeScript (Deno) que chama Resend API para email e WhatsApp Business API.
  • Camada 3 — Worker local: timer no app do paciente com retry automático se Internet falhar.
Se o pg_cron falhar (ex.: manutenção do Supabase), o worker local ainda envia. Se a Internet do paciente falhar, o servidor já tentou. Redundância tripla.
16Como funciona o Audit Log?

O Audit Log usa triggers PL/pgSQL no PostgreSQL. Para cada tabela crítica (profiles, appointments, triagens, faturas):

  • Existe um trigger AFTER INSERT OR UPDATE OR DELETE.
  • O trigger chama fn_audit_trigger() que insere na tabela audit_log: user_id, action (INSERT/UPDATE/DELETE), table_name, old_data, new_data, timestamp.
  • A tabela audit_log só tem políticas SELECT para admins — nenhum utilizador pode apagar registos de auditoria.
17O sistema funciona offline? Como?

Funciona parcialmente offline com limitações:

  • O que funciona offline: visualização de dados já carregados (cache local), interface do app, leitura de QR Codes, acesso a fichas previamente abertas.
  • O que não funciona offline: criar/editar consultas (requer sincronização com o servidor), enviar lembretes, ver actualizações em tempo real.
  • Implementação: AsyncStorage (React Native) para cache local + React Query com staleTime para não re-buscar dados desnecessariamente.
Limitação honesta: não foi implementado full offline-first com sincronização de conflitos. Para isso seria necessário uma biblioteca como WatermelonDB ou PowerSync.

19Que padrão de arquitectura foi usado no código da app?

A app usa uma arquitectura baseada em separação de responsabilidades:

  • lib/supabase.ts — configuração do cliente Supabase (singleton).
  • hooks/use*.ts — custom hooks React para encapsular queries (ex.: usePatients(), useAppointments()).
  • components/ — componentes UI reutilizáveis sem lógica de negócio.
  • app/(tabs)/ — ecrãs (Expo Router, baseado em ficheiros como Next.js).
  • contexts/ — estado global (AuthContext, ThemeContext).
20Como o sistema escala para múltiplas clínicas?

O sistema foi desenhado para ser multi-tenant:

  • Cada utilizador tem um clinic_id (UUID) associado no perfil.
  • As políticas RLS incluem AND clinic_id = (SELECT clinic_id FROM profiles WHERE id = auth.uid()).
  • Cada clínica vê apenas os seus próprios dados, mesmo partilhando a mesma base de dados.
  • Supabase Cloud escala horizontalmente — sem necessidade de gerir instâncias.

3. Segurança e Base de Dados

21O que é Row Level Security (RLS) e por que é importante?

RLS é uma funcionalidade do PostgreSQL que permite definir políticas de acesso ao nível de cada linha da tabela. Sem RLS, se um utilizador conseguir acesso à API, pode ver todos os dados. Com RLS:

  • Um paciente faz GET /rest/v1/appointments — só recebe as suas consultas.
  • Um dentista faz a mesma query — só recebe as consultas dos seus pacientes.
  • Esta filtragem acontece no PostgreSQL, antes de retornar dados — não pode ser contornada pelo cliente.
Exemplo de política: CREATE POLICY "paciente_ver_proprios" ON appointments USING (paciente_id = auth.uid());
22O que é SECURITY DEFINER e qual era o problema na view triagem?

SECURITY DEFINER é uma propriedade de funções e views PostgreSQL que faz a execução correr com as permissões do criador, não do utilizador que está a chamar.

  • Problema: a view public.triagem estava marcada como SECURITY DEFINER. Isso significa que quando um utilizador normal a consultava, o PostgreSQL executava como se fosse o admin — ignorando completamente as políticas RLS.
  • Risco: um paciente poderia ver triagens de outros pacientes.
  • Correcção: ALTER VIEW public.triagem SET (security_invoker = true); — agora a view respeita as permissões do utilizador que faz a query.
23O que é o search_path mutável e por que é uma vulnerabilidade?

O search_path define em que schemas o PostgreSQL procura objectos quando o nome não é qualificado. Se uma função SECURITY DEFINER não fixa o search_path:

  • Um utilizador malicioso pode criar uma tabela ou função com o mesmo nome numa schema diferente.
  • Quando a função SECURITY DEFINER corre, pode usar o objecto malicioso em vez do legítimo.
  • Este ataque chama-se search path injection ou schema spoofing.

Correcção: adicionar SET search_path = public na definição de cada função SECURITY DEFINER:

CREATE OR REPLACE FUNCTION public.is_admin() RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$ SELECT EXISTS(SELECT 1 FROM profiles WHERE id = auth.uid() AND tipo = 'admin'); $$;
24O que é REVOKE EXECUTE e por que foi necessário?

Por padrão no PostgreSQL, quando cria uma função, todos podem executá-la (incluindo utilizadores anónimos). No Supabase, a API expõe funções via /rest/v1/rpc/nome_funcao.

  • Problema: funções admin como admin_delete_dentista() eram acessíveis sem autenticação pela API pública.
  • Correcção: REVOKE EXECUTE ON FUNCTION public.admin_delete_dentista FROM public, anon;
  • Depois: GRANT EXECUTE ON FUNCTION public.admin_delete_dentista TO authenticated; — só utilizadores com JWT válido.
25Como são protegidas as imagens médicas no Storage?

O bucket triagens armazena imagens de triagens clínicas. As políticas implementadas:

  • INSERT: só authenticated podem fazer upload — USING (auth.role() = 'authenticated')
  • SELECT (paciente): só o dono do ficheiro — USING (auth.uid()::text = (storage.foldername(name))[1])
  • SELECT (staff): dentistas e secretários podem ver qualquer imagem — via função is_healthcare_pro()
  • Problema anterior corrigido: havia uma política de LIST que permitia listar todos os ficheiros anonimamente — eliminada.
26Os dados dos pacientes estão encriptados?

Sim, em dois níveis:

  • Em trânsito: toda a comunicação usa HTTPS/TLS 1.3 — dados encriptados entre o app e o servidor.
  • Em repouso: Supabase Cloud usa AES-256 para encriptação do disco onde o PostgreSQL está armazenado (AWS RDS com encriptação activada).
Limitação: não foi implementada encriptação campo-a-campo (ex.: encriptar individualmente o campo historico_clinico). Isso exigiria bibliotecas como pgcrypto ou Vault, aumentando a complexidade operacional. Para dados altamente sensíveis (ex.: HIV+), seria recomendado.
27Como são geridos os papéis/roles no sistema?

Os papéis são armazenados na coluna tipo da tabela public.profiles com valores: admin, dentista, secretario, paciente.

  • Quando o utilizador autentica, o seu auth.uid() é usado para consultar o perfil.
  • Funções PL/pgSQL (is_admin(), etc.) verificam o papel e são usadas nas políticas RLS.
  • O papel não é armazenado no JWT directamente (por segurança — evita que o utilizador modifique o token).
  • O papel é sempre consultado da base de dados, que é a fonte de verdade.
28Como são prevenidos ataques SQL Injection?

Múltiplas camadas de protecção:

  • Supabase JS SDK: usa sempre queries parametrizadas — nunca concatenação de strings.
  • PostgREST: as queries são geradas pelo PostgREST que usa prepared statements.
  • RLS: mesmo que uma query maliciosa passe, as políticas RLS limitam os dados acessíveis.
  • Validação no cliente: inputs são validados com bibliotecas como Zod antes de enviar para a API.
Exemplo seguro: supabase.from('patients').select('*').eq('id', userId) — o SDK garante que userId é escapado correctamente, nunca concatenado.
29O sistema está em conformidade com alguma lei de protecção de dados?

O design segue os princípios do RGPD/GDPR europeu e da Lei de Protecção de Dados de Angola:

  • Minimização de dados: só são recolhidos dados necessários para a gestão clínica.
  • Consentimento: pacientes aceitam termos ao registar-se.
  • Direito de acesso: pacientes vêem os seus próprios dados no app.
  • Audit Log: registo de quem acedeu/alterou que dados e quando.
  • RLS: isolamento de dados entre utilizadores.
Para conformidade total com LGPD Angola, seriam necessários: política de privacidade formal, consentimento granular para cada tipo de dado, e possivelmente um DPO (Data Protection Officer). Identificado como trabalho futuro.
30Que tipos de testes de segurança foram realizados?

Foram realizados os seguintes testes de segurança:

  • Supabase Security Linter: ferramenta automática que analisou 16 categorias de vulnerabilidades comuns — todos os issues foram corrigidos.
  • Teste de políticas RLS: foram criadas contas de teste com papéis diferentes e verificado que cada utilizador só acede aos seus dados.
  • Teste de funções sem autenticação: chamadas à API sem JWT validaram que funções admin retornam erro 401/403.
  • Verificação de headers HTTP: HTTPS forçado, CORS configurado para apenas os domínios autorizados.
Não foi feito penetration testing profissional (pen test). Para um sistema em produção com dados médicos reais, seria recomendado contratar uma empresa especializada.
31O que é pg_cron e como foi usado?

pg_cron é uma extensão do PostgreSQL que permite agendar queries SQL como se fosse um cron job no Linux. Foi usado para:

  • Correr de hora em hora: SELECT cron.schedule('0 * * * *', $$CALL send_appointment_reminders()$$);
  • A função SQL verifica consultas nas próximas 24 horas que ainda não tiveram lembrete enviado.
  • Para cada consulta, chama pg_net.http_post() para invocar a Edge Function de envio.
A extensão pg_net foi movida para um schema privado (extensions) como parte das correcções de segurança — evita que utilizadores normais chamem HTTP arbitrariamente via API.

4. Funcionalidades e Decisões de Design

33Como funciona o QR Code de check-in do paciente?

Cada paciente tem um QR Code único gerado a partir do seu user_id (UUID). No fluxo de check-in:

  • O paciente abre o app e mostra o QR Code na recepção.
  • A secretária usa o scanner do app Windows/Web para ler o QR.
  • O sistema identifica o paciente, confirma a presença e actualiza o estado da consulta para "arrived".
  • O dentista vê em tempo real (via Realtime) que o paciente chegou.

O QR Code não contém dados pessoais — apenas o ID. Se interceptado, não há informação sensível.

34O que é o "Motor de Triagem"? Usa realmente IA?

O motor de triagem é um sistema de regras (rule-based system), não IA generativa.

  • Com base nos sintomas seleccionados pelo paciente (ex.: "dor intensa", "sangramento"), o sistema sugere prioridade (urgente/normal) e especialidade (ortodontia, endodontia).
  • É uma tabela de mapeamento: sintoma → {prioridade, especialidade} — lógica implementada em TypeScript no cliente.
  • Não usa Machine Learning nem modelos de linguagem (GPT, etc.).
Honestidade para a defesa: chamar de "IA" seria exagero. É um sistema de regras baseado em conhecimento clínico básico. Implementar IA real (diagnóstico por imagem de raio-X) é identificado como trabalho futuro.
35Como funciona a integração com o WhatsApp?

Via WhatsApp Business Cloud API (Meta):

  • Requer conta Business verificada no Facebook/Meta Business Manager.
  • As mensagens usam Message Templates pré-aprovados pela Meta (obrigatório para mensagens de negócio).
  • A Edge Function faz um HTTP POST para https://graph.facebook.com/v18.0/{phone_id}/messages com o token da API.
  • É necessário o número de telefone do paciente no formato internacional (+244...).
Limitação: a API gratuita tem limite de 1000 conversas/mês. Para volumes maiores, é necessário plano pago da Meta.
36Como é gerada a fatura em PDF?

O PDF é gerado no cliente (app) usando a biblioteca expo-print que converte HTML para PDF:

  • Os dados da fatura são buscados da base de dados (tabela faturas).
  • Um template HTML é preenchido com os dados (nome, serviços, valores, data).
  • expo-print.printToFileAsync(html) gera o PDF localmente no dispositivo.
  • O PDF pode ser partilhado via expo-sharing (Email, WhatsApp, Downloads).
37Por que se escolheu Supabase em vez de Firebase?

Comparação directa:

Base de dadosPostgreSQL (relacional, SQL)Firestore (NoSQL, documentos)

Para um sistema clínico com dados relacionais complexos (paciente → consultas → triagens → faturas), SQL relacional é mais adequado que NoSQL.
38Como é feita a navegação no app (roteamento)?

O sistema usa Expo Router v3, que implementa roteamento baseado em ficheiros (file-based routing) — semelhante ao Next.js App Router:

  • app/(tabs)/home.tsx → rota /home
  • app/(auth)/login.tsx → rota /login
  • Middleware de autenticação em app/_layout.tsx redireciona para login se não autenticado.
  • Grupos de rotas com layouts partilhados (ex.: tab bar só aparece após autenticação).
39Como são tratados os estados de carregamento e erros na UI?

Foram usados dois mecanismos principais:

  • React Query (TanStack Query): gerencia estados isLoading, isError, data automaticamente. Inclui re-fetch automático, retry em falha e cache.
  • Componentes condicionais: if (isLoading) return <LoadingSpinner />, if (error) return <ErrorMessage />.
  • Toast notifications: feedback visual de sucesso/erro em acções do utilizador.
40O sistema tem um design system / componentes reutilizáveis?

5. Metodologia e Processo

43Por que foi escolhida a metodologia Scrum?

Scrum foi escolhido porque:

  • Os requisitos de um sistema clínico não são totalmente conhecidos no início — emergem com o uso.
  • Sprints de 2 semanas permitem mostrar protótipos reais a profissionais de saúde e recolher feedback.
  • A iteratividade reduz o risco de construir funcionalidades que ninguém usa.
  • É a metodologia mais adoptada globalmente (State of Agile 2024: 87% das equipas ágeis usam Scrum).
Adaptação para projecto individual: como não há equipa, o "Sprint Review" foi feito com o orientador e com profissionais da clínica piloto. O "Daily Scrum" foi substituído por diário de desenvolvimento.
44Qual foi a maior dificuldade técnica do projecto?

Resposta honesta — três desafios principais:

  • Sincronização multiplataforma: garantir que o estado do app é consistente entre Mobile, Desktop e Web com Realtime — geriu race conditions e actualizações duplicadas.
  • Configuração de segurança PostgreSQL: entender e implementar correctamente RLS, SECURITY DEFINER, search_path e políticas de Storage foi mais complexo do que esperado — exigiu auditoria completa.
  • Build Android com Expo/EAS: configuração do keystore, permissões de manifesto e assinatura do APK para distribuição sem loja.
45Como foi feita a modelagem de dados (design do banco)?

O processo foi:

  • Levantamento de requisitos: entrevistas com dentistas e secretárias de clínicas angolanas.
  • Diagrama ER: modelagem das entidades e relações (paciente, consulta, triagem, fatura).
  • Normalização: aplicação das formas normais (até 3FN) para evitar redundância.
  • UUIDs como PK: em vez de integers sequenciais — evita exposição de quantidade de registos e facilita merge de dados de múltiplas clínicas.
  • Soft delete: coluna deleted_at em vez de DELETE real — preserva auditoria.
46Que ferramentas foram usadas para controlo de versão e gestão do projecto?
  • Git + GitHub: controlo de versão com branches por feature.
  • VS Code: editor principal com extensões ESLint, Prettier, TypeScript.
  • Supabase Studio: interface visual para gestão da base de dados e testes de RLS.
  • Expo Go: teste rápido no telemóvel durante desenvolvimento.
  • Postman: teste das Edge Functions e endpoints da API REST.

Sim, em dois níveis:

  • Clínica piloto: uma clínica odontológica em Luanda foi envolvida nos testes. Dentistas, secretárias e pacientes usaram o sistema durante o período de testes.
  • Feedback recolhido: ajustes na UI (tamanho de texto), adição de campo de urgência na triagem, e melhoria no fluxo de faturação foram resultados directos dos testes com utilizadores.
Limitação: não foi feito um teste formal com métricas de usabilidade (SUS - System Usability Scale). Os testes foram qualitativos — baseados em observação e entrevista.

6. Perguntas Difíceis / "Pegadinhas" do Júri

51🔴 "O Supabase pode fechar o serviço. O que acontece aos dados dos pacientes?"

Resposta honesta e técnica:

  • Supabase é open-source (MIT). Em caso de descontinuação, o código pode ser auto-hospedado em qualquer servidor Linux com Docker.
  • O Supabase permite export completo da base de dados PostgreSQL em formato SQL a qualquer momento.
  • Os dados não ficam presos — PostgreSQL é um padrão aberto, compatível com qualquer cloud (AWS RDS, Azure Database, etc.).
  • Plano de contingência documentado: script de backup semanal via pg_dump + armazenamento no Google Drive da clínica.
52🔴 "Um paciente poderia aceder às fichas de outro paciente se descobrisse o UUID?"

Não. Esta é exactamente a protecção que o RLS oferece:

  • Mesmo que um atacante conheça o UUID de outro paciente, a query GET /rest/v1/profiles?id=eq.UUID_ALHEIO retorna [] (lista vazia).
  • O PostgreSQL aplica a política USING (id = auth.uid()) antes de retornar qualquer dado — a filtragem acontece no servidor, não no cliente.
  • A API não expõe o UUID de outros utilizadores em nenhum endpoint acessível.
Teste realizado: conta de paciente A não consegue ver dados de paciente B, mesmo com conhecimento do UUID — retorna sempre lista vazia.
53🔴 "Um médico poderia modificar dados de faturação?"

Não, por design do controlo de acesso:

  • A tabela faturas tem políticas RLS separadas por papel.
  • Dentistas têm apenas política SELECT nas faturas dos seus pacientes.
  • INSERT/UPDATE/DELETE em faturas está restrito ao papel secretario e admin.
  • As funções de faturação têm REVOKE para o papel authenticated genérico, com GRANT específico para secretario.
54🔴 "O sistema não tem testes unitários automatizados. Como garante que o código funciona?"

Resposta honesta:

  • Não foram implementados testes unitários com Jest/Vitest ou testes de integração automatizados — limitação real do projecto.
  • O TypeScript actua como primeira linha de "testes" — erros de tipo são detectados em compile time.
  • Testes manuais foram realizados com utilizadores reais na clínica piloto.
  • As políticas RLS foram testadas manualmente via Supabase Studio com diferentes contas.
Para um sistema em produção médica, testes automatizados seriam obrigatórios — especialmente para funções de faturação e gestão de medicação. Identificado como trabalho futuro prioritário.
55🔴 "O que acontece se o Supabase tiver downtime? A clínica fica sem sistema?"

Verdade: se o Supabase Cloud estiver em baixo, operações que requerem Internet não funcionam. Mitigações:

  • Supabase Pro tem SLA de 99.9% de uptime (~8.7h de downtime/ano).
  • Cache local (AsyncStorage/React Query) permite consultar dados já carregados offline.
  • Para continuidade crítica: imprimir lista de consultas do dia de manhã cedo — procedimento de contingência documentado.
  • Trabalho futuro: implementar offline-first completo com sincronização de conflitos (ex.: PowerSync).
56🔴 "A app está publicada na Google Play Store?"

Não, actualmente é distribuída como APK directo (sideload):

  • A Google Play Store exige revisão de apps médicas que pode demorar semanas/meses e requer documentação de conformidade específica.
  • Para o contexto académico e piloto, a distribuição por APK directo é suficiente.
  • O APK foi gerado e assinado com keystore via EAS Build — é instalável em qualquer Android sem Play Store.
  • Publicação na Play Store está identificada como próximo passo após a defesa.
57🔴 "Este sistema já é HIPAA/HL7 compliant? Pode ser usado em hospital real?"

Resposta directa: não é certificado para uso hospitalar em contexto regulado.

  • HIPAA (EUA) e GDPR (Europa) têm requisitos específicos que vão além do implementado.
  • HL7 FHIR (padrão de interoperabilidade clínica) não foi implementado.
  • Para uso em hospital público em Angola seria necessário aprovação do MINSA e auditoria externa.
  • Para clínicas dentárias privadas: o sistema cobre os requisitos práticos de gestão clínica, mas sem certificação formal.
O objectivo académico é demonstrar a viabilidade técnica. Certificação regulatória é processo separado que exige equipa jurídica e de saúde.
58🔴 "Como define o sucesso deste projecto?"

O projecto é bem-sucedido segundo 3 métricas:

  • Técnica: sistema funcional em 4 plataformas, 0 erros de compilação TypeScript, 16 vulnerabilidades de segurança corrigidas, lembretes automáticos funcionais, auditoria completa e 2FA WhatsApp operacional.
  • Académica: demonstração aplicada de competências em desenvolvimento multiplataforma, base de dados relacional, segurança e arquitectura de software — objectivos do curso de Computação Móvel.
  • Social/Impacto: clínica piloto reduziu consultas perdidas por falta de lembrete em ~40% durante o período de testes. Sistema foi adoptado pela equipa após o piloto.
A maior satisfação é ver dentistas e secretárias reais a usar o sistema com entusiasmo, substituindo papéis por fichas digitais.
59🔴 "Por que implementou a Autenticação em 2 Etapas (2FA) e por que usou o WhatsApp em vez de apenas SMS ou Google Authenticator?"

A autenticação por dois factores (2FA/MFA) é fundamental em sistemas de saúde devido ao sigilo médico e protecção de dados:

  • Contexto Angolano: O SMS internacional tem custo elevado por envio e taxa de entrega inconsistente. O WhatsApp, por outro lado, possui penetração de quase 100% entre smartphones em Angola e é gratuito para quem recebe através de pacotes de dados de redes sociais das operadoras (Unitel/Africell).
  • Arquitectura: Ao fazer login, se o utilizador tiver 2FA activo, um código criptográfico temporário de 6 dígitos é gerado e despachado via API do WhatsApp e registado com tempo de expiração curto (5 minutos).
  • Flexibilidade Híbrida: O sistema suporta simultaneamente TOTP (aplicativos autenticadores padrão) e envio por WhatsApp, com modal responsivo adaptável a Mobile, Web e PWA.
Resultado: Segurança de nível bancário sem custos de SMS e com entrega imediata no telemóvel do profissional.
60🔴 "Por que o 2FA é exigido para Admin, Secretária e Dentista, mas NÃO para o Paciente comum?"

Esta é uma decisão intencional de Trade-off entre Segurança e Usabilidade (UX):

  • Cargos com Privilégios (Admin, Secretária, Dentista): Têm acesso a bases de dados completas, prontuários de dezenas de utentes, prescrições e valores de faturamento. Uma invasão destas contas compromete a clínica inteira. Daí a obrigatoriedade de 2FA.
  • Utentes / Pacientes: Acedem apenas à sua própria ficha e procuram agilidade para agendar uma consulta. Impor 2FA ao paciente causaria fricção, abandono do agendamento e sobrecarga nas receções.
Princípio de Engenharia: A intensidade da segurança deve ser proporcional ao risco e ao nível de privilégio do perfil.
61🔴 "Como funciona a arquitectura do Log de Auditoria (Audit Log) do sistema?"

O Audit Log foi desenhado para garantir conformidade e rastreabilidade total (governança de dados):

  • Tabela Dedicada: Tabela audit_logs no PostgreSQL com colunas: user_id, user_email, action, resource, ip_address, created_at e campo metadata do tipo JSONB.
  • Imutabilidade: Políticas RLS estritas onde utilizadores normais não têm permissão de UPDATE ou DELETE na tabela de logs — apenas o trigger ou serviços autorizados fazem INSERT.
  • Interface de Gestão (Admin): Ecrã dedicado com busca em tempo real, filtros por tipo de evento (Auth, Triagem, Agendamento, Faturação) e expansão interativa do payload JSON.
62🔴 "Como garantiu a responsividade de modais e fluxos complexos em Web, PWA e Mobile?"

Utilizámos uma estratégia multiplataforma com React Native e CSS adaptativo:

  • Prevenção de Colisão com Teclado: Uso de KeyboardAvoidingView com comportamento condicional (padding no iOS, height no Android e neutro em Web).
  • Containers Flexíveis: Modais com maxHeight: '92%', ScrollView interno com keyboardShouldPersistTaps="handled", eliminando cortes de conteúdo em ecrãs pequenos.
  • Centralização de Telas Administrativas: Containers com maxWidth: 900 e alignSelf: 'center' no desktop para manter leitura agradável tanto em monitores ultrawide como em smartphones.
63🔴 "Como está desenhado o módulo de Relatórios do Administrador e a contabilidade em Kwanzas?"

O módulo de relatórios foi reorganizado em 4 abas estruturadas:

  • 1. Visão Geral: Cards de KPIs em tempo real (Total de Utentes, Dentistas, Secretários, Consultas e Triagens) e balanço financeiro distinguindo Receita Estimada vs. Receita Realizada em Kwanzas (Kz).
  • 2. Dentistas: Filtro em tempo real de dentistas, métricas de triagens atendidas e botão de exportação de relatório individual em PDF.
  • 3. Secretários: Desempenho e listagem da equipa de receção com exportação individual em PDF.
  • 4. Central de PDFs: Geração de Relatório Consolidado Geral do Sistema em PDF formatado, com cabeçalho institucional e data/hora de emissão.
64🔴 "Como funciona a experiência inicial com o carrossel automático de boas-vindas?"

Na tela inicial de apresentação:

  • Um carrossel dinâmico rotaciona automaticamente a cada 10 segundos exibindo imagens e mensagens institucionais sobre saúde oral e acolhimento.
  • A transição é suave, sincronizada com indicadores interativos (dots) e temporizadores controlados no ciclo de vida do React Native.
  • Os assets gráficos foram optimizados e incorporados localmente na compilação, permitindo carregamento instantâneo mesmo offline.
