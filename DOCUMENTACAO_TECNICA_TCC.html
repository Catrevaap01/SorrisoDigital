1. Visão Geral do Projecto

O TeOdonto Angola é um sistema digital de gestão odontológica desenvolvido para clínicas dentárias em Angola. A aplicação permite o controle completo do fluxo clínico — desde a pré-triagem digital feita pelo paciente, passando pelo agendamento, atendimento clínico, prescrição médica, até ao controle financeiro.

🎯 Objectivo Central

Digitalizar o fluxo completo de uma clínica odontológica angolana, eliminando processos manuais (fichas de papel, agendas físicas) e garantindo rastreabilidade, segurança e eficiência no atendimento.

💡 Por que Supabase e não Firebase?

O Supabase utiliza PostgreSQL (base de dados relacional), que permite Row Level Security (RLS) nativo — essencial para um sistema de saúde onde dados clínicos devem ser estritamente controlados. O Firebase (NoSQL) não oferece este nível de controle granular ao nível da linha.

3.3 Padrão Provider → Hook → Screen

O projecto segue o padrão React Context + Custom Hooks para gestão de estado global. Os Contexts encapsulam estado partilhado, os Hooks expõem lógica reutilizável, e os Screens consomem ambos para renderizar a UI.

// Exemplo do padrão:

// 1. Context (AuthContext.tsx)
const AuthContext = createContext<AuthContextValue>(undefined);
export const AuthProvider = ({ children }) => {
  const [user, setUser] = useState(null);
  // ... lógica de autenticação
  return <AuthContext.Provider value={{ user, login, signOut }}>...

// 2. Hook (useAuth)
export const useAuth = () => useContext(AuthContext);

// 3. Screen
const HomeScreen = () => {
  const { user, profile } = useAuth();
  return <View>Olá, {profile?.nome}</View>;
};

5. Módulo de Autenticação e Segurança

O ficheiro AuthContext.tsx é o coração do sistema de segurança, com 1382 linhas de código. É o Context Provider mais complexo do projecto.

5.1 Funcionalidades do AuthContext

FuncionalidadeDescrição
Login/RegistoAutenticação via email/senha com Supabase Auth. Suporte a MFA (TOTP).
Sessão ÚnicaApenas 1 dispositivo activo por conta. Novo login expulsa sessões anteriores via Realtime Broadcast + Storage Event.
Perfil (Profile)Busca e normaliza dados do perfil. Resolve província por ID. Suporta fallback para admin client em caso de RLS.
MFA (2FA)Suporte a autenticação de dois factores via TOTP (Google Authenticator, Authy).
Timeout de InactividadeLogout automático após 2 minutos sem interacção (configurável).
HeartbeatVerificação de integridade de sessão a cada 1.5 segundos (fail-safe contra falhas Realtime).
Tab/Instance IDID único por aba (web) ou por dispositivo (mobile). Usado para detecção de sessão duplicada.
Força Mudança de SenhaUtilizadores com senha temporária são forçados a alterá-la no primeiro acesso.
Completar PerfilPacientes auto-registados devem preencher telefone e província antes de usar o sistema.
Províncias de Angola18 províncias angolanas com normalização de nomes (acentos, variantes de escrita).

🔐 Mecanismo de Sessão Única (Anti-Concurrent-Login)

Quando um utilizador faz login, o sistema:

  1. Gera um tabInstanceId único para esta sessão
  2. Grava o ID em localStorage (web) e na coluna last_session_id da tabela profiles
  3. Envia um Broadcast Realtime para todos os outros dispositivos/abas
  4. Invalida sessões anteriores via supabase.auth.signOut({ scope: 'others' })
  5. Outras abas detectam via Storage Event e fazem logout imediato (<1s)

16. Sistema em Tempo Real (Realtime)

O sistema utiliza Supabase Realtime baseado em Websockets para garantir actualizações instantâneas entre todos os utilizadores conectados.

FicheiroFunção

⚡ Performance do Realtime

O sistema está configurado com eventsPerSecond: 20 e heartbeatIntervalMs: 15000. O polling de mensagens é de 3 segundos como fallback. A reconexão automática após falha usa backoff exponencial com máximo de 10 segundos.

20. Perguntas Frequentes na Defesa

❓ "Por que React Native e não Flutter ou desenvolvimento nativo?"

React Native permite código único para Android, iOS, Web e Desktop. O ecossistema JavaScript/TypeScript é mais acessível, e o Expo simplifica drasticamente o build e deploy. Flutter exigiria aprender Dart, e desenvolvimento nativo duplicaria o esforço.

❓ "Como funciona a segurança de dados clínicos?"

Três camadas: (1) Autenticação via Supabase Auth com email/senha e suporte a MFA; (2) Row Level Security (RLS) no PostgreSQL que garante que cada utilizador aceda apenas seus dados; (3) Sessão única que impede acesso concorrente e expulsa sessões anteriores em menos de 1 segundo.

❓ "O que acontece se a internet cair durante o uso?"

O offlineSyncService utiliza uma fila offline armazenada no AsyncStorage. Acções como criação de triagens e agendamentos são armazenadas localmente. Quando a conectividade é restaurada, o NetworkContext detecta e o processOfflineQueue() sincroniza automaticamente com o servidor, notificando o utilizador do resultado.

❓ "Como o sistema distingue entre os 4 perfis de utilizador?"

Cada utilizador tem um campo tipo na tabela profiles (paciente/dentista/secretário/admin). O AppNavigator lê esse campo e renderiza condicionalmente o Stack de navegação correspondente. As RLS policies no PostgreSQL usam este campo para controlar o acesso aos dados.

❓ "Por que Supabase e não um backend tradicional (Node.js/Django)?"

O Supabase oferece: (1) PostgreSQL gerido com RLS nativo; (2) Autenticação pronta; (3) Realtime via Websockets sem configuração; (4) Edge Functions para lógica server-side; (5) Storage para imagens. Tudo num único serviço, reduzindo drasticamente o tempo de desenvolvimento e a complexidade de infraestrutura.

❓ "Qual o diferencial do projecto em relação a outros sistemas de gestão?"

O TeOdonto foi desenhado especificamente para a realidade angolana: (1) Suporte às 18 províncias de Angola; (2) Modo offline para áreas com conectividade instável; (3) Multiplataforma (mobile para pacientes, web/desktop para a clínica); (4) Triagem digital que reduz o tempo de espera; (5) 9 especialidades odontológicas configuráveis.

❓ "Como garantem que o dentista vê apenas os pacientes dele?"

Duas camadas: (1) No frontend, o DashboardScreen filtra consultas e triagens pelo dentista_id do utilizador logado; (2) No backend, as políticas RLS do PostgreSQL impedem qualquer SELECT que tente aceder dados de outro dentista, mesmo que o frontend seja manipulado.

❓ "Como funciona a geração de PDF?"

O pdfReportService.ts gera templates HTML com CSS embutido (logotipo, tabelas, formatação profissional). O expo-print converte esse HTML em PDF directamente no dispositivo. O ficheiro pode ser partilhado via expo-sharing ou impresso. Funciona offline.

❓ "Quantas linhas de código tem o projecto?"

O projecto tem mais de 50 telas, 22 serviços, 9 hooks, 11 componentes e 15 utilitários. Apenas o AuthContext.tsx tem 1382 linhas. O SecretarioDashboardScreen tem 67.1 KB. Estima-se mais de 30.000+ linhas de código TypeScript/TSX no total.
